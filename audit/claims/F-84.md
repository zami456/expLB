# F-84 — the cluster-permutation test completes the pre-registration: p = 0.38

**Source:** `kd/docs/FINDINGS.md:3357` (batch W5C-ledger).

## The claim, in one sentence
A Maris–Oostenveld cluster-based label-permutation test on the kd matched-slice layer profile
(20 layers on passA, mean pooling, k = 5, B = 200, control = a matched random projection) gives
an observed largest contiguous-positive cluster mass of **0.9155** with clusters
**[0.916, 0.059]**, a null mean of **0.8871** and a null 95th percentile of **2.5787**, hence
**p = 0.38** — the band is not distinguishable from what label noise produces, and the
pre-registered prediction (p > 0.2) was right.

## What I did
On the lab PC, read-only (`W5C_labA.py`, `W5C_labB.py`):
1. Loaded `run-premise/cluster_perm_kd_matched.json`, printed every key, and **recomputed** the
   p-value, null mean and 95th percentile from the stored 200-value null.
2. Recomputed the cluster statistic myself from the stored `observed_margins` (count the
   positive layers, find the contiguous runs, sum each run's margins) and compared it with the
   stored `observed_clusters` / `observed_max_mass`.
3. Read `src/assistant_axis_ndif/30c_cluster_perm.py` for the control type, the run dir, B, k
   and the permutation scheme.
4. Read both runs of the test out of `logs/premise_extras.log` — the 2026-09-21 one and the
   2026-09-22 re-run — to see whether the RF-13 regeneration changed anything.

## Verdict: **HOLDS**

- **Every stated number reproduces.** 0.9155 ✓, [0.916, 0.059] ✓ (0.91552 / 0.05881), null mean
  0.8871 ✓ (0.887128), null 95th percentile 2.5787 ✓ (exactly, via `np.percentile`, linear
  interpolation), p = 0.38 ✓ (76 of 200 null draws ≥ the observed, the plain proportion; the
  more conservative (76+1)/(200+1) = 0.3831 does not change the reading), B = 200 ✓,
  20 layers ✓ (0…76 in steps of 4), k = 5 ✓, passA ✓, mean pooling ✓.
- **The statistic is internally consistent**, which is the check that matters most here: I
  re-derived the clusters from the stored per-layer margins without using the stored clusters,
  and the contiguous positive run over layers 28–48 (indices 7–12) sums to exactly the reported
  maximum mass, with the isolated layer 76 giving the second cluster.
- **The control is what the caveat says it is** — a matched **random** projection at the same k
  (`30c_cluster_perm.py:101–120`), not dataset-PCA, and the permutation is applied identically
  at every layer (line 134), so the null preserves the between-layer correlation as claimed.
- **"The observed mass sits essentially on the null mean"** ✓ (0.9155 vs 0.8871), and the
  pre-registered prediction in the script's own docstring (written before the run, p > 0.2) is
  quoted correctly.
- Two trivia: the entry says the run took 9.1 min; the only surviving status line (the 09-22
  re-run) says 9.3 min — the 09-21 status line was destroyed by the RF-14 guard bug. And the
  caveat "B = 200 is modest" is right: the null's 95th percentile (2.58) is nearly three times
  the observed mass, so this test had no chance of being close.

### The RF-13 question, answered
The JSON carries mtime **2026-09-22 16:07:02**, i.e. it was regenerated inside the boot-trigger
wave, and the original file is gone. **But a pre-wave comparison does exist after all:**
`logs/premise_extras.log` retains both runs, and the 2026-09-21 16:09 run printed
**identical** values (7/20 positive, mass 0.9155, p = 0.3800, null mean 0.8871, 95th pct
2.5787). So the regeneration reproduced the original exactly and the copy I read is
trustworthy. (`30c_cluster_perm.py` builds its own label permutations from `run-coords/passA`
and never reads `run-crossgen/passA/splits.json`, so the crossgen split warning noted in RF-13
does not touch it.) No BH q-value is quoted here, so the RF-13 test-family problem does not
apply.

one place.
