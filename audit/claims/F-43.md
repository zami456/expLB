# F-43 — "The coords OOM was a per-process cap all along; truncation was the only lever"

Batch **M1-method-claims**. Source: `kd/docs/FINDINGS.md:1186` (2026-09-20).

## The claim, restated
The OOM that three rounds of budget-shrinking could not fix is a **per-process** memory cap on the
NDIF deployment, not GPU pressure, proved by the error message: a **562.00 MiB** allocation fails
while **55.13 GiB of the GPU's 139.80 GiB is free**. Table: F-41 (attn 2.0→0.75) = 57 OOMs / 14
permanent; F-42 (attn→0.55) = **50 OOMs / 12 permanent**, allocations fell **902 → 438 MiB**;
session_batches 4→1 still OOMs at "1 batches, 5250 padded tokens"; **max_length 2048→1024 = 0
OOMs**. Truncation is cheap because HP-KR assistant spans are **p50 = 5, p90 = 10, p99 = 13,
max = 70** tokens and **none exceeds 1024**.

## What I did
Same three log scripts as F-42 (`audit/scripts/claims/M1_logs{,2,3}.py`) plus
`audit/scripts/claims/M1_span.py` for the span quantiles, all read-only on the lab PC against
`logs/scale_coords_8b.log` and `run-coords/passB/harm-pressure-knowledge-report/rows.jsonl`.

## Results

### 1. The error line — VERBATIM, and it says more than the entry quotes
Log line 6529, `2026-09-20 18:02:46,173`:
```
session attempt 4/4 (1 batches, 5250 padded tokens) failed: NNsightException: OutOfMemoryError:
CUDA out of memory. Tried to allocate 562.00 MiB. GPU 0 has a total capacity of 139.80 GiB of
which 55.13 GiB is free. Process 3623751 has 18.14 GiB memory in use. Process 3605328 has 3.36
GiB memory in use. Process 3654827 has 7.72 GiB memory in use. Process 366716...
```
All three quoted numbers (562.00 MiB / 139.80 GiB / 55.13 GiB) are exact. The continuation the
entry omits — **four or more named processes each holding GPU memory** — is the strongest evidence
for the per-process reading and should be quoted in the thesis instead of the two lines alone.
(The per-process *mechanism* remains an inference; what is measured is that ~55 GiB is free, the
allocation is 562 MiB, and several processes share the card.)

### 3. "allocations fell 902 → 438 MiB" — both numbers exist, the pairing is loose
Largest `Tried to allocate` per phase:

| phase | n | max | min | last |
|---|---:|---:|---:|---:|
| ≤17:32:28 (attn 2.0) | 67 | 1955.8 MiB | 656.0 | 738.0 |
| 17:32:29–17:48:37 (attn 0.75) | 64 | 764.0 | 286.0 | 444.0 |
| 17:48:38–18:02:05 (attn 0.55) | 52 | 562.0 | 230.0 | 302.0 |
| 18:02:06–18:04:19 (sess 1) | 5 | 562.0 | 498.0 | 498.0 |

**902.0 MiB occurs only in the pre-17:32 attn=2.0 phase**; 438.0 MiB occurs at 18:00:05–18:00:34
inside the attn=0.55 phase. So "902 → 438" spans *two* budget changes, not the single F-42 step the
table row attributes it to. The sentence's point (allocations really did shrink while the failure
persisted) is supported; the specific pair is not a within-step comparison.

### 5. The stated limitation is real and is carried in code
`run_scale_coords.ps1:117-120` repeats it: "the 70B passB ran at max_length 8192. These rungs run
at 1024, so absolute AUROCs are NOT comparable across model size." Confirmed against
`run_coords_chain.ps1:95` (`--max_length 8192`). This is load-bearing for every 3B/8B-vs-70B
comparison (F-63, F-100–F-102).

## Verdict
**PARTLY HOLDS.** The diagnosis, its evidence line, the "still OOM at 1 batch / 5250 tokens" step,
the clean post-1024 window and four of five span statistics all reproduce exactly. Two secondary
figures do not: the F-42 row's OOM count (measured 52, stated 50) and p99 (measured 12, stated 13).
Neither moves the conclusion.

Confidence **HIGH** (primary log, own counting script, four independent quantile conventions).
Importance **HIGH for the methods chapter** — the 1024-vs-8192 truncation it justifies is the
stated limitation behind every cross-scale comparison.
