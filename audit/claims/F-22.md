# F-22 — "`1_generate_ndif.py` never got the exc_tail fix"

**Batch:** W5B-ledger · **Checked:** 2026-09-23 · source `kd/docs/FINDINGS.md:392`

## The claim, restated
Every failed NDIF session in the 2026-09-20 8B generation run logged only
`NNsightException: Traceback ... remote.py, line 567` and nothing else, because the session
retry handler in `src/assistant_axis_ndif/1_generate_ndif.py` used `str(e)[:200]`; nnsight wraps
the remote failure in a *client-side* traceback, so a prefix slice is spent entirely on local
frames. `8_coords_ndif.py` and `ndif_common.exc_tail()` had been fixed for this in Pass B; this
script was missed. Switching to the last line surfaced F-21's OOM on the first retry.
Cited source: `1_generate_ndif.py:145`. No metric — a code + log claim.

## What I did
- `audit/scripts/claims/F-22.py` (local, git only): locates `str(e)[:200]` and `exc_tail` in every
  committed version of the script and of its siblings, and prints the handler context at the
  pre-fix commit `106d09f` and at HEAD.
- `audit/scripts/claims/W5B_labB.py` (lab, read-only): prints the `session attempt` lines with
  context from `logs/scale_8b_generate.log` (pre-fix) and `logs/scale_3b_generate.log` (post-fix).

## Verdict — HOLDS
Every substantive element checks out: the `str(e)[:200]` handler, the truncated log line ending in
`Fi` right after `remote.py, line 567`, `ndif_common.exc_tail` and the equivalent inline fix in
`8_coords_ndif.py` both present at the pre-fix commit, and the OOM surfacing on the **first** retry
after the change (3B log line 172).

Three caveats the entry does not carry:
1. **The cited line is off.** `:145` is the *fix's comment* line in the post-fix file; in the version
   that actually misbehaved (`106d09f`) the slice is at **L146**.
2. **The fix is still incomplete inside the same file.** `generate_batch`'s handler at **HEAD line
   186** still uses `str(e)[:200]`. The entry's own lesson — "when a failure mode is fixed, grep the
   siblings" — was not applied to the sibling handler 40 lines below it.
3. **"the fourth instance"** is a count I did not verify. Session mining (`b035ccb3`, 2026-09-20
   09:46) records a *fifth* instance found and fixed in `2_activations_ndif.py` the same day, which
   the entry does not mention; git shows that file going from 2 to 1 `str(e)[:200]` at `3dfdb67`.
