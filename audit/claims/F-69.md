## Verdict — HOLDS (composition claim), with two qualifications
The repair is real and every post-repair number is exact, including the slice size and split
recomputed from the released CSV with my own implementation of the slice rule. The gate line and the
36-minute elapsed time are verbatim.

Qualifications:
1. **The "before" figures (98 rows, 89/9) cannot be recomputed.** The 200-row subsample they describe
   was overwritten by the top-up. The status file confirms only `passA=200 passC=200`. The direction
   of the claim is not in doubt (a denial-matched slice of a label-stratified 200-row subsample must
   be small), but "9 honest deniers" is print-only.
2. **The passC row of the table is stale.** F-69 marks passC "200 / 98 / 89-9 / pending"; the same
   status file shows passC completed 23 minutes later with the same 2,139 rows, and passC's slice is
   today also 258 at 124/134. (The ledger supersedes this in F-71.)
3. "5.22 GB" matches neither the incremental (5.08 GB) nor the total (5.61 GB) measurement — a
   print-only figure that does not reproduce. Immaterial.

**Version note:** the status file was **appended** (not truncated) by the 2026-09-22 15:47 re-run,
so the 09-21 gate lines survive; that re-run was a no-op (`adds ~0 rows`) and its two rclone steps
failed (`exit 1`), which is part of RF-10/RF-13.
