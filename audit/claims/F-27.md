## Where the 1.07% comes from, and why it matters
The constant is not only in F-27: `scale/scripts/score_summary.py` prints
`"(70B reference: 16/1500 = 1.07%)"` as a hardcoded literal, and its module docstring repeats
"The 70B scored 0-1 on 16 of 1,500 rollouts (1.1%)". So every rung report produced by that script
carries the same unsupported denominator. The paper16 score directory holds 25 files and 1,350
rollouts; F-30 (written the same day) uses 1,350 / 0.89% and explicitly notes "the 70B rung has 1,350
rollouts against the others' 2,500". No file I can find holds 1,500 judged paper16 rollouts.
This is a **DOC-ONLY / code-literal number with no supporting file**, and the "2.7x" headline is
derived from it.

## Verdict
**PARTLY HOLDS.** The generation facts and every per-group judge number reproduce exactly — the
21-role subset is recoverable from the surviving files, which is a stronger check than the entry
itself offered. But the 70B comparison denominator (1.07%, 16/1,500) is not supported by any score
file (measured 0.89%, 12/1,350), so the entry's title claim — "the 8B breaks character 2.7x more" —
is wrong as stated; the correct multiple on the surviving data is **3.2x** (F-27's own 8B rate) or
**3.6x** (F-30's final 8B rate).
Confidence **HIGH** (all counts recomputed from the score JSONs).
Importance **LOW-MEDIUM** for the paper — the usable-corpus conclusion ("97% survives, the rung is
usable") is unaffected — but **the 1,500/1.07% literal should be removed from `score_summary.py`**,
because it silently contaminates any future rung report.
